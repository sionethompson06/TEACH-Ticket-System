# TEACH Ticket System — Decision Log

This log records confirmed architectural and service-design decisions, along with decisions that remain open. Confirmed entries use the date the decision was recorded. Status values are `Confirmed`, `Proposed`, or `Superseded`.

| D-012 | 2026-08-12 | Attachments are intended for a TEACH-owned, restricted Google Shared Drive — never an individual employee's personal Drive.                                                                                                                           | Confirmed | Keeps attachment ownership and access control with the organization rather than an individual account.                                                                                                                                                                                    | TEACH changes its file-storage platform.                                                                                    |
| D-013 | 2026-08-12 | Configuration access and confidential-content access are separate permissions.                                                                                                                                                                        | Confirmed | A system administrator configuring the platform should not automatically be able to read confidential ticket content.                                                                                                                                                                     | Not anticipated; revisit only if this proves operationally unworkable.                                                      |
| D-014 | 2026-08-12 | The project will be implemented in small, approved phases.                                                                                                                                                                                            | Confirmed | Reduces risk of overbuilding before the core workflow is validated with real users.                                                                                                                                                                                                       | Not anticipated; revisit only by explicit leadership direction.                                                             |
| D-015 | 2026-08-12 | Use the stable Next.js App Router with strict TypeScript and a `src/` directory structure.                                                                                                                                                            | Confirmed | Matches the documented future technical direction; App Router is the current stable Next.js paradigm and strict TypeScript catches type errors before runtime.                                                                                                                            | Next.js deprecates the App Router or a materially different framework is selected.                                          |
| D-016 | 2026-08-12 | Use npm with a single committed `package-lock.json` as the sole package manager.                                                                                                                                                                      | Confirmed | Avoids multiple lockfiles and keeps installs reproducible across contributors and CI.                                                                                                                                                                                                     | Team standardizes on a different package manager.                                                                           |
| D-017 | 2026-08-12 | Adopt Node.js 24 LTS as the runtime baseline (`.nvmrc` and `package.json` `engines`).                                                                                                                                                                 | Confirmed | Node 24 is the current LTS release at the start of implementation, giving the longest support window.                                                                                                                                                                                     | Node 24 reaches end-of-life or a newer LTS becomes the team standard.                                                       |
| D-018 | 2026-08-12 | Use Tailwind CSS for the minimal application shell's styling.                                                                                                                                                                                         | Confirmed | Matches the documented future technical direction and avoids hand-rolled CSS for a simple, responsive shell.                                                                                                                                                                              | A design system or component library is adopted later.                                                                      |
| D-019 | 2026-08-12 | Use Vitest and React Testing Library for component-level tests.                                                                                                                                                                                       | Confirmed | Vitest integrates cleanly with the Vite-based tooling Next.js's ecosystem already uses, and React Testing Library encourages accessible, user-facing queries over implementation detail.                                                                                                  | A different testing framework becomes the team standard, or end-to-end testing is introduced in a later phase.              |
| D-020 | 2026-08-12 | Use GitHub Actions for automated quality checks (lint, format, typecheck, tests, build) on every push and pull request.                                                                                                                               | Confirmed | Keeps quality checks automatic and visible without requiring a separate CI provider; uses only read-only permissions and no secrets.                                                                                                                                                      | The team adopts a different CI provider or adds deployment automation requiring different permissions.                      |
| D-021 | 2026-08-12 | Use Drizzle ORM and Drizzle Kit for typed schema definition and versioned SQL migration generation.                                                                                                                                                   | Confirmed | Drizzle keeps migrations as plain, reviewable SQL rather than an opaque engine format, and its TypeScript-first schema matches the project's typed stack without adding a heavier ORM.                                                                                                    | The team adopts a different ORM/migration toolchain.                                                                        |
| D-022 | 2026-08-12 | Keep the database layer provider-neutral (plain PostgreSQL dialect, no provider-specific SDK) until a managed provider is selected.                                                                                                                   | Confirmed | No managed PostgreSQL provider has been chosen yet; avoiding provider-specific libraries keeps the schema and connection code portable across whichever provider is eventually selected.                                                                                                  | A managed PostgreSQL provider is selected.                                                                                  |
| D-023 | 2026-08-12 | Use node-postgres (`pg`) with a lazy, server-side-only connection-pool factory for database access.                                                                                                                                                   | Confirmed | `pg` is the standard, provider-neutral PostgreSQL driver for Node; a lazy factory ensures importing database modules, running `next build`, or loading the status page never requires a database connection or environment variable.                                                      | A different runtime driver becomes necessary for a selected provider.                                                       |
| D-024 | 2026-08-12 | Commit versioned SQL migrations (and Drizzle's migration journal/snapshots) generated from the typed schema, reviewed before commit.                                                                                                                  | Confirmed | Plain committed SQL is auditable in code review and reproducible across environments; migrations are generated from the schema, never hand-written against it, to keep them from silently disagreeing with the types.                                                                     | Not anticipated; revisit only if the migration tool changes.                                                                |
| D-025 | 2026-08-12 | Migrations and seeds run only via explicit administrative commands (`db:migrate`, `db:seed`), never automatically during install, build, start, or deployment.                                                                                        | Confirmed | Automatic migrations during a build or deploy risk silently altering a shared database; requiring an explicit, human-triggered command keeps schema changes deliberate and reviewable.                                                                                                    | Not anticipated; revisit only by explicit leadership direction.                                                             |
| D-026 | 2026-08-12 | Canonical reference records (the TEACH organization, schools, and service locations) use stable, hand-assigned UUIDs that never regenerate between seed runs.                                                                                         | Confirmed | Stable IDs make the seed idempotent and let other data reference these records predictably across environments and reseeds.                                                                                                                                                               | Not anticipated; revisit only if reference data is restructured.                                                            |
| D-027 | 2026-08-12 | Use PGlite strictly as in-memory, test-only database infrastructure for the automated integration test suite, never as a production option.                                                                                                           | Confirmed | PGlite lets the test suite prove real PostgreSQL migrations and constraints work end-to-end with no external database or credentials, while keeping the production database question fully open.                                                                                          | Not anticipated; revisit only if the testing strategy changes.                                                              |
| D-028 | 2026-08-12 | The managed production PostgreSQL hosting provider remains an open decision.                                                                                                                                                                          | Confirmed | No provider has been evaluated or selected; the schema and connection pattern are deliberately provider-neutral until this is resolved.                                                                                                                                                   | A managed PostgreSQL provider is evaluated and selected.                                                                    |
| D-029 | 2026-08-13 | Use Better Auth (`better-auth` + `@better-auth/drizzle-adapter`), pinned to the exact stable `1.6.27` release, for all OAuth/OIDC, session, and CSRF handling.                                                                                        | Confirmed | A maintained authentication library avoids hand-rolled OAuth/JWT/session/CSRF code, which is high-risk to get right; pinning to an exact stable release (never a beta/RC) keeps behavior predictable and reviewable.                                                                      | A security or maintenance issue requires a different version or library.                                                    |
| D-030 | 2026-08-13 | Use Google's immutable per-account `sub` claim, never the email address, as the identity anchor for a provider account record.                                                                                                                        | Confirmed | An email address can change while `sub` cannot; anchoring identity to a mutable value risks silently attaching one person's history to another.                                                                                                                                           | Not anticipated; revisit only if Google changes its identity-claim guarantees.                                              |
| D-031 | 2026-08-13 | Every account provisioned through Google Workspace sign-in is fixed to the canonical TEACH organization and the nonprivileged Requester base role, enforced redundantly at the API-field, hook, and database-constraint layers.                       | Confirmed | Phase 3 is scoped to authentication only; every account must start from the same, deliberately minimal, non-elevated state, enforced at multiple layers so no single code change can silently grant more.                                                                                 | Phase 4 introduces a role/permission system that supersedes the fixed Requester default.                                    |
| D-032 | 2026-08-13 | Request only the minimal OpenID Connect scopes (`openid`, `email`, `profile`) from Google, and never persist an OAuth access token, refresh token, ID token, or password.                                                                             | Confirmed | The only use of Google here is identity verification at sign-in; no broader scope or stored credential is needed, and one not requested or stored can never leak.                                                                                                                         | A future phase needs to act on a user's behalf against a Google API, requiring separately reviewed scope/storage additions. |
| D-033 | 2026-08-13 | Use database-backed sessions with an 8-hour maximum lifetime and Secure, `HttpOnly`, `SameSite=Lax` cookies.                                                                                                                                          | Confirmed | Database-backed sessions can be revoked server-side by deleting a row, unlike stateless JWTs; an 8-hour cap limits the exposure window of a stolen session without disrupting a normal workday.                                                                                           | Operational experience shows the session lifetime is too short or too long for real usage patterns.                         |
| D-034 | 2026-08-13 | A failed sign-in attempt always shows the same generic denial message, regardless of which specific verification check failed.                                                                                                                        | Confirmed | Revealing which check failed would let an outsider probe for which email addresses or organizations exist; a single generic message leaks nothing.                                                                                                                                        | Not anticipated; revisit only if support workflows require more specific in-app guidance.                                   |
| D-035 | 2026-08-13 | Build only a simplified three-level MVP access-control model for Phase 4 — Requester, Department Agent, System Administrator — before any richer role/permission/campus-grant system.                                                                 | Confirmed | The core help-desk workflow (tickets, routing, communication) doesn't exist yet; building department-manager roles, campus grants, confidential queues, and audit workflows before that core exists risks over-engineering a permission system for a workflow that hasn't been validated. | The core ticket workflow (Phase 5+) is working and validated, and richer authorization is explicitly approved.              |
| D-036 | 2026-08-13 | Model "department agent" as a simple membership table — presence of a row means the user is an agent for that department — instead of a role-grant framework.                                                                                         | Confirmed | A plain membership table is the smallest structure that satisfies "a user may belong to IT, Facilities, or both" without introducing manager levels, expiring grants, or a capability matrix the MVP doesn't need yet.                                                                    | Department-manager-level distinctions become a confirmed, approved requirement.                                             |
| D-037 | 2026-08-13 | Designate a system administrator with one explicit, database-set boolean column (`user.is_system_administrator`), defaulting `false`, never seeded, never client-settable.                                                                            | Confirmed | This is the smallest design that fits the existing `user` table cleanly; a hidden administrator, bootstrap account, or email-based allowlist would be a harder-to-audit shortcut around the same requirement.                                                                             | Multiple administrator levels (e.g., configuration vs. confidential-content authority) become a confirmed requirement.      |
| D-038 | 2026-08-13 | Keep the authorization module (`src/authz/`) independent of Better Auth's initialization; resolve the current actor from a validated session's user id plus a fresh, parameter-free database read, never from client-supplied role/membership claims. | Confirmed | Testability without Google credentials and a hard architectural guarantee against trusting forged client input are both satisfied by the same design: the actor-resolution function's signature has no field a client could use to claim a role.                                          | Not anticipated; revisit only if the authorization module's responsibilities expand significantly.                          |
| D-039 | 2026-08-13 | Treat service locations as ticket routing/filtering metadata during the MVP, not a permission-scoping system.                                                                                                                                         | Confirmed | Campus-scoped visibility (e.g., for principals) is a deferred, post-MVP concern (Phase 9); introducing location-based access control before it's needed would add complexity the current phase doesn't require.                                                                           | Campus/principal visibility (Phase 9) becomes a confirmed, approved requirement.                                            |
